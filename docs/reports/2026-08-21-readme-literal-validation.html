Why this report exists

The previous report tested the engine thoroughly — all 6 schemas, all 3 sinks, FK-orphan checks, both environments — but it did that using a custom Python script hitting POST /api/ddl/load, an endpoint I chose to interpret as "feed it a brand-new schema." That is not what the README actually documents. The README's real, only documented walkthrough uses POST /api/schema/load — live-DB introspection, a different code path — and that walkthrough had never once been run, by me or anyone, against the current code.

Put plainly: the first report proved the tool works. It didn't prove the instructions work. Those turned out to be different claims, and the gap between them contained three real, blocking bugs.

Method

For each environment, in order:

  1. Wipe it back to nothing (Docker volumes deleted, K8s namespaces deleted, or terraform destroy)
  2. Rebuild it using only the exact commands printed in the README — no custom scripts, no manual patches, no shortcuts
  3. Run the README's documented "Fire a load run" sequence verbatim, all 7 commands, in the order shown
  4. Verify the results against real Postgres data directly — not API status codes

The rule for this pass, set explicitly: any bug found gets fixed, and then the entire validation restarts from Docker Compose — all three environments, in full, again. No partial re-checks. This is why it took three complete passes to get one clean one.

The three bugs

Bug 6 — env.example passwords never matched the real Postgres containers. Every database except bankschema failed on the very first non-trivial command, from a genuinely fresh cp env.example .env: 
{"status":500,"error":"Internal Server Error","message":"Schema inspection failed: Failed to initialize pool: FATAL: password authentication failed for user \"bankinguser\""}

Root cause: env.example shipped DB_PASS_*=changeme placeholders. Every postgres-* service in docker-compose.yml has its real password hardcoded directly in its own environment: block — the containers never read credentials from .env at all. bankschema only ever "worked" by accident: it's the one database where the app service's own environment: block also hardcodes DB_USER_BANKSCHEMA/DB_PASS_BANKSCHEMA, silently overriding the mismatched .env value the same way every other database needed but didn't have. This means the documented Compose walkthrough could not have worked for 5 of 6 databases on a first-time setup, on any machine, ever — pre-existing, not introduced by this session's earlier changes.

Fix: env.example's DB_PASS_* now match each service's real hardcoded password, with a comment explaining why they must stay in sync manually.
Bug 7 — azure-deploy.sh's Grafana rollout timeout was too short for the new sidecar. On a fresh AKS node pool that had never cached grafana/grafana-image-renderer:latest, the extra image pull pushed the Grafana deployment's total startup time past the script's 120-second wait. The script exited with error: timed out waiting for the condition before applying Ingress or printing the service URLs — a hard failure, not a warning.

Root cause: the grafana-image-renderer sidecar added during the previous test run is a second image pull on top of Grafana's own (~58s observed for Grafana alone). Confirmed the pod does reach 2/2 Running on its own — just past the old timeout, not actually broken.

Fix: bumped the timeout to 300s.
Bug 8 — README's K8s namespace table was stale. Still listed 4 databases and pg-exporter × 4 under testfixtures-data / testfixtures-monitoring, left over from before the Salesforce databases and their exporters were added earlier this session.
Fix: table updated to the real 6-database, 6-exporter, renderer-sidecar-included state.
